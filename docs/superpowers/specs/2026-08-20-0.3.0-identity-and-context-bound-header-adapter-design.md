# 0.3.0 Identity and ContextBound HeaderProtocolAdapter Design

**Status:** Approved on 2026-08-20

**Date:** 2026-08-20

**Target repository:** this repository (`gmcrypto-envelope-lite`)

**Target version:** 0.3.0

## 1. Purpose

Open 0.3.0 development on `main` without waiting for crates.io publication of 0.2.0, then close the documented gap that `HeaderProtocolAdapter` can only emit `AuthenticationContext::legacy()`.

Today a header-mapped integration that wants `AuthenticationMode::ContextBound` must write a custom `ProtocolAdapter`. The README already shows the encoding that new integrations should use. This phase makes that encoding a first-class, exclusive schema acknowledgement on the existing adapter, without changing `ProtocolAdapter`, transcript framing, or envelope cryptography.

This specification does not change code, does not retarget `v0.2.0`, and does not publish to crates.io.

## 2. Current baseline

Facts verified at design time against annotated tag `v0.2.0` (`c7075b75d7460327d741814a15ff28fa1c1ec478`), which is also `main` at design time:

- Crate version is `0.2.0`. The GitHub repository is public. The crate is **not** on crates.io; live `cargo publish --locked` failed with 403 because the local token lacked publish permission. Publication is delayed by owner decision and, when it happens, must run from `git checkout v0.2.0`, not from a later `main`.
- `HeaderSchemaBuilder` requires `.legacy_authentication()` or `build()` returns `AdapterErrorKind::MissingField`. `HeaderProtocolAdapter::request_authentication_context` always returns `AuthenticationContext::legacy()`. `parse_response` always attaches `AuthenticationContext::legacy()` and does not read the request-id header from the response.
- `ProtocolAdapter` is object-safe, unsealed, and implemented outside the crate. Adding a required trait method is breaking (`docs/api-stability.md`).
- `AuthenticationMode::ContextBound` already exists. Transcript version 1 is `0x01 || u64be(domain_len) || domain || u64be(context_len) || context || u64be(plaintext_len) || plaintext`. The adapter supplies only the context bytes; the SDK frames them.
- `AuthenticationContext::context_bound` rejects empty bytes. `ProtocolRequestContext` rejects trimmed-empty operation strings and CR/LF. Request metadata likewise rejects trimmed-empty request ids.
- The README primary example and `examples/build_request.rs` already construct request context as `operation={op}&request-id={id}` and response context as `request-id={id}` from an echoed request-id header. That is the encoding this design pins.
- `ci/check-public-api.sh` derives snapshot filenames from `Cargo.toml`. `CipherLocation` stays exhaustive. Fuzz `transport_parts` / `typed_headers` schemas use `.legacy_authentication()`.
- Versioned documents: security model, API-stability policy, engineering evidence, and cryptographic inventory are all **version 2**. This phase does not revise those policy versions.

## 3. Goals

- Move crate identity on `main` to 0.3.0 so 0.2.0 remains the immutable tagged line.
- Teach `HeaderProtocolAdapter` to produce and consume ContextBound authentication through an explicit schema acknowledgement, using one crate-owned encoding.
- Keep `.legacy_authentication()` as the required acknowledgement for plaintext-only header mappings.
- Leave `ProtocolAdapter`, `SecureClient`, `AuthenticationMode`, envelope crypto, and fuzz corpus bytes unchanged except where tests must observe the new acknowledgement.

## 4. Non-goals

- SM4-CCM, replay helpers, streaming, or server-side open-request / seal-response APIs.
- Charter §8 min-and-newest `gmcrypto-core` CI on every PR (still deferred).
- Live `cargo publish`, retargeting `v0.2.0`, or storing `CARGO_REGISTRY_TOKEN` in GitHub Actions.
- Configurable context field lists, format strings, or URL-encoding of field values.
- A second public adapter type (`BoundHeaderProtocolAdapter` or similar).
- Passing `ClientConfig` / `AuthenticationMode` into `HeaderProtocolAdapter`.
- Comparing the echoed response request-id to the outbound request-id inside `parse_response` or `SecureClient`. Request/response correlation remains an application check.
- New public error variants.
- A new fuzz target or ContextBound `transport_parts` schema in this phase.
- Bumping security-model, API-stability, evidence, or inventory **document** versions.

## 7. Train B — adapter

### 7.1 Schema acknowledgement

`HeaderSchema` stores a private authentication kind: `Legacy` or `ContextBound`. It is not a public enum.

`HeaderSchemaBuilder` keeps two booleans (or equivalent flags):

- `.legacy_authentication()` sets the legacy flag. Calling it twice is last-wins (still `true`).
- `.context_bound_authentication()` sets the bound flag. Calling it twice is last-wins.

`build()`:

| Flags | Result |
| --- | --- |
| neither | `AdapterErrorKind::MissingField` (today’s missing-acknowledgement path) |
| both | `AdapterErrorKind::InvalidMapping` |
| only legacy | `HeaderSchema` kind `Legacy` |
| only context-bound | `HeaderSchema` kind `ContextBound` |

All existing required mappings remain required in both kinds. `Debug` for the builder reports both flags. `Debug` for `HeaderSchema` may show the kind; it must not print context bytes (there are none stored on the schema).

`legacy_authentication` rustdoc must stop saying the adapter cannot produce context-bound authentication. It selects plaintext-only signatures for this schema. `context_bound_authentication` rustdoc states: both peers reconstruct the encodings in §7.2 from typed fields; this is not AEAD, not replay protection, and not request/response correlation; `ClientConfig` must pin `AuthenticationMode::ContextBound` separately.

### 7.2 Pinned encodings

These are **construction recipes**. Verifiers rebuild the bytes from typed header fields. They must not parse the concatenated string as a query. `&` and `=` inside field values are allowed and do not require percent-encoding.

**Request** (`request_authentication_context`), UTF-8:

```text
operation={operation}&request-id={request_id}
```

`operation` is `ProtocolRequestContext::operation()`. `request_id` is `context.metadata().request_id()`. Identity fields, request time, API version, and certificates are not included. Convert with `AuthenticationContext::context_bound`. If that constructor fails, return `AdapterErrorKind::InvalidField` (defensive; the format prefix is never empty once operation and request id have already passed context validation).

**Response** (`parse_response`), UTF-8, ContextBound schemas only:

```text
request-id={request_id}
```

`request_id` is the trimmed nonempty value of the header whose name is `HeaderSchema`’s `request_id_header`, looked up on the **response** with the same case-insensitive name match as other response mappings. Same errors as other required response headers:

- missing → `MissingField`
- empty after trim → `InvalidField`
- case-insensitive duplicate → `DuplicateField`
- value rejected by `HeaderValue` → `InvalidField`

Legacy `parse_response` continues to ignore that header.

The echoed request-id is **not** compared to any outbound request-id. `parse_response` still does not receive the outbound `ProtocolRequestContext`.

### 7.3 Collision rule

For ContextBound schemas only, `validate_collisions` inserts `request_id_header` into the **response** name set. `HeaderName` equality is case-insensitive (canonical form), so `X-Demo-Request-Id` colliding with `x-demo-response-signature` is `InvalidMapping` the same as an exact-case clash. A ContextBound schema whose request-id header name equals `response_signature_header`, `response_wrapped_key_header`, `response_remote_signing_certificate_header`, or a header-placed `response_cipher` name fails `build()` with `InvalidMapping`.

Legacy schemas do not gain this extra response collision, because they do not read request-id on the response.

### 7.4 `ProtocolAdapter` and `SecureClient`

No trait methods added or given defaults. `HeaderProtocolAdapter` remains one type.

The adapter still does not see `ClientConfig`. Mode/context mismatch stays `Error::AuthenticationContext` at `SecureClient` (bound schema + `LegacyPlaintext` client, and the inverse). There is no negotiation and no fallback.

`build_request` mapping is unchanged for both kinds: it still emits operation, request-id, and the other schema headers. ContextBound does not add headers; it only changes which `AuthenticationContext` is returned on seal and open.

### 7.5 Public API

Train B adds `pub fn HeaderSchemaBuilder::context_bound_authentication(self) -> Self` under default features. Regenerate both 0.3.0 snapshots. The default-features snapshot is no longer content-identical to 0.2.0.

`ProtocolAdapter`, `CipherLocation`, `AuthenticationContext`, and `AuthenticationMode` stay as they are.

## 8. Tests

### 8.1 Train A

Existing release-document, package, RC, workflow, and public-API contract tests must pass after identity substitution. No new behavioral tests.

### 8.2 Train B

Prefer extending `tests/protocol_adapter.rs` (and a `SecureClient` mismatch case) over new files.

Required coverage:

- `build()` neither acknowledgement → `MissingField`; both → `InvalidMapping`; either alone with a complete mapping → `Ok`.
- ContextBound `request_authentication_context` equals `AuthenticationContext::context_bound(b"operation=demo-operation&request-id=demo-request-1")` when using the existing demo fixtures (adjust the literal to whatever `request_context()` already uses).
- ContextBound `parse_response` with an echoed request-id header (including a case-differing header name) yields `request-id={id}`.
- ContextBound `parse_response` missing / empty / duplicate request-id header → `MissingField` / `InvalidField` / `DuplicateField`.
- ContextBound schema whose `request_id_header` collides with a response mapping → `InvalidMapping`.
- Legacy `parse_response` still succeeds without a request-id header and still returns `AuthenticationContext::legacy()`.
- `SecureClient` with a ContextBound schema and `AuthenticationMode::LegacyPlaintext` (and the inverse) returns `Error::AuthenticationContext`.
- Existing legacy protocol-adapter, support-schema, AEAD, redacted-debug, and fuzz fixtures that call `.legacy_authentication()` remain passing without encoding changes.

Do not switch `fuzz/fuzz_targets/support.rs` to ContextBound. Existing corpus bytes stay valid.

`complete_schema_builder()` remains legacy-only (still calls `.legacy_authentication()`). ContextBound tests start from `schema_builder_omitting(Some(RequiredMapping::LegacyAuthentication))` and then call `.context_bound_authentication()`, or an equivalent helper that never sets both flags.

The `RequiredMapping::LegacyAuthentication` omitting loop stays a missing-acknowledgement check: omitting that mapping still calls neither method and must remain `MissingField`. Do not add a second required mapping that every schema must set.

## 10. Implementation notes

- `AuthenticationContext::context_bound` returns `crate::Error`. Map it to `AdapterErrorKind::InvalidField` at the adapter boundary, matching `examples/build_request.rs` and `tests/secure_client.rs`.
- Response header scan: extend the existing `parse_response` loop rather than a second pass, so duplicate detection covers the request-id slot the same way as signature / wrapped-key / cert / cipher slots.
- Do not URL-encode. Do not include a trailing delimiter. Do not add spaces around `=` or `&`.
