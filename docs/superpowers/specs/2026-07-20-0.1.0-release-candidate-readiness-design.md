# 0.1.0 Release Candidate Readiness Design

**Status:** Approved design

**Date:** 2026-07-20

**Target package:** `secure-envelope-lite` 0.1.0

## 1. Purpose

Move the completed neutral secure-envelope refactor from a healthy development baseline to a reproducible 0.1.0 release candidate. The phase stabilizes the public API, connects security claims to verification evidence, makes release-candidate construction repeatable, and defines the external approvals that must remain outside the public repository.

This phase produces an RC-quality package and an evidence checklist. It does not publish the crate. `publish = false` remains in place until private compatibility, security, legal, and release approvals have been completed through authorized processes.

## 2. Current baseline

At design time, the repository has these properties:

- the open-source extensibility refactor is implemented on `main`;
- the worktree is clean;
- 110 unit and integration tests pass;
- formatting and Clippy with warnings denied pass;
- the boundary-scanner self-test and current-worktree scan pass;
- CI covers stable Rust on Linux, macOS, and Windows plus Rust 1.85 MSRV on Linux;
- Cargo metadata identifies version 0.1.0, but publishing is disabled;
- no release tag or public API compatibility baseline exists; and
- private exact-wire compatibility, organization-specific scanning, independent security review, and legal approval are external gates.

The repository is therefore technically mature enough for release-candidate preparation, but it must not be described as independently audited or ready for production deployment.

## 3. Goals

- Review and stabilize every public type, method, trait, constant, and root re-export before the first release candidate.
- Publish a versioned security model that defines supported threats, trust boundaries, security claims, and explicit non-claims before building the engineering evidence map.
- Make correct and incorrect uses of legacy and context-bound authentication clear in rustdoc and executable examples.
- Trace each security claim and trust boundary to implementation evidence, automated tests, or an explicitly external verification gate.
- Inventory the cryptographic backend, pinned version, feature selection, unsafe boundary, and update policy.
- Add focused adversarial and fuzz coverage where untrusted structured input crosses into parsing, mapping, or cryptographic envelope processing.
- Provide one fail-closed, reproducible repository-owned command for building and checking a release candidate from a named Git commit.
- Verify both the clean source export and the unpacked Cargo package, not only the working tree.
- Produce a public, non-sensitive checklist that separates completed repository checks from outstanding private or human approvals.
- Define promotion states so a repository-built RC cannot be mistaken for an externally approved or release-authorized artifact.
- Keep private protocol mappings, identities, fixtures, denylist entries, and review evidence outside the public repository.

## 4. Non-goals

- Publishing to crates.io, pushing a release tag, or changing `publish = false`.
- Claiming an independent cryptographic or security audit.
- Adding an HTTP client, asynchronous runtime, retry policy, endpoint management, or TLS configuration.
- Adding a new cipher suite, AEAD profile, HSM/KMS integration, or pluggable cryptographic primitive layer.
- Importing the deployed protocol mapping or private compatibility fixtures.
- Rewriting Git history or publishing the current repository history directly.
- Guaranteeing zeroization or constant-time behavior inside third-party dependencies.
- Treating an RC checklist as a substitute for private compatibility, security, or legal approval.

## 5. Design principles

### 5.1 Freeze before expanding

The phase reviews the existing API rather than adding product capabilities. Changes are limited to documentation, release tooling, verification, and corrections required by a concrete usability or security finding. An API change must be justified before the first compatibility baseline is recorded.

### 5.2 Evidence over assertions

Every security or release-readiness statement must point to one of:

- a deterministic automated test;
- a repeatable release-check command and artifact;
- a focused fuzz target with retained regression input; or
- an external gate whose owner and required result are documented.

Passing public CI cannot be used to imply that private compatibility, independent review, or legal approval has occurred.

The engineering evidence map is an internal assurance aid. It is not an audit, certification, warranty, proof of cryptographic security, or evidence of side-channel resistance.

### 5.3 Fail closed

Release tooling stops on command failure, missing required files, unexpected package roots or archives, scanner errors, checksum errors, dirty or ambiguous source state, and unfulfilled repository-owned gates. It never silently skips a failed check and never publishes automatically.

### 5.4 Preserve the public boundary

All repository additions use neutral fictitious data. External policy and compatibility tooling may consume a clean export or package, but its inputs and detailed outputs remain outside the checkout. Only a non-sensitive approval state and artifact identity may be transferred into the release decision.

## 6. Workstream A: public API stabilization

### 6.1 API inventory

Inventory every item re-exported from `src/lib.rs` and every public member reachable from those items. The review covers:

- construction and validation paths;
- ownership and borrowing behavior;
- error and panic contracts;
- `Send + Sync` and immutability expectations;
- secret-bearing or unverified-data exposure;
- extensibility of `ProtocolAdapter`;
- future compatibility of public enums; and
- deliberate versus accidental convenience APIs.

Public enums are reviewed explicitly for whether downstream exhaustive matching is intended. Where future variants are plausible, the implementation plan must decide before the RC baseline whether to use `#[non_exhaustive]`, retain an intentionally closed enum, or expose a different compatibility boundary. The decision is recorded rather than applied mechanically.

The inventory also performs an unsafe-by-default review of compatibility surfaces. `ClientConfig` already requires an explicit authentication mode, and `HeaderSchema` already requires explicit legacy enablement; these fail-closed properties must remain tested. Each public legacy or shared-role convenience is reviewed for naming, construction friction, and nearby `# Security` documentation. The phase does not move APIs into a feature or module merely for appearance: such a breaking change requires evidence that the existing explicit opt-in is insufficient.

### 6.2 Documentation contract

Public items receive sufficient rustdoc to explain purpose, invariants, validation, failure conditions, and security-sensitive caveats. Documentation must distinguish:

- role-specific `KeyMaterial::new` from deliberate shared-role conveniences;
- `LegacyPlaintext` compatibility from preferred `ContextBound` authentication;
- signature authentication from confidentiality and TLS responsibilities;
- verified plaintext from unauthenticated response metadata; and
- SDK responsibilities from application-owned replay and request/response correlation.

At least one executable happy-path example covers request construction and verified response opening using neutral data. Security-sensitive conveniences include warnings close to the API, not only in the README.

Examples must state that every envelope profile in this crate retains the fixed-IV SM4-CBC compatibility construction. `ContextBound` is the preferred authentication mode where the wire can support it, but examples must not imply that it supplies AEAD, repairs CBC leakage, or removes transport, replay, and correlation responsibilities.

### 6.3 Compatibility baseline

After review fixes pass all checks, capture a checked-in, sorted text snapshot of the public API for 0.1.0 RC using a pinned `cargo-public-api` version. CI regenerates the snapshot with the same version and rejects drift. The implementation plan must pin a tool version that can inspect this crate on the release toolchain; the API tool does not replace the separate Rust 1.85 compilation gate. The baseline is created only after API decisions are complete so it does not legitimize accidental surface area.

The documented 0.1.x policy follows Semantic Versioning while acknowledging that 0.x development may include breaking releases. Patch releases within 0.1.x must not intentionally break the recorded API; an intentional breaking change advances the minor version and is documented.

## 7. Workstream B: security assurance

### 7.1 Security claims and non-claims

Before adding evidence or tests, consolidate the existing README and security-policy statements into a versioned, public security-model document. It defines:

- protected assets and attacker-controlled inputs;
- local process, key-loading, adapter, transport, and remote-peer trust boundaries;
- confidentiality and authentication properties asserted by each supported mode;
- legacy plaintext-signature and fixed-IV CBC limitations;
- application responsibilities for TLS, replay defense, request/response correlation, endpoint selection, retry safety, and key rotation;
- SDK-owned zeroization claims and dependency-owned memory limitations; and
- explicit non-claims covering universal constant-time behavior, timing/cache/power side-channel resistance, formal verification, FIPS or GM certification, independent audit, compromised-process protection, and security of third-party allocations.

README, rustdoc, examples, and release summaries may link to or summarize this document but must not assert a stronger property. Changes to the claim set require corresponding evidence-map review and create a new RC artifact identity.

### 7.2 Engineering evidence map

Create a repository document mapping every claim in the security model to its evidence. The document starts with: “This engineering evidence map is not an independent audit, certification, warranty, or proof of cryptographic security.” It covers at least:

| Security property | Required evidence |
| --- | --- |
| Directional signing, decryption, verification, and encryption roles | Key-role and two-party integration tests |
| Context-bound transcript framing | Exact byte-vector and mismatch tests |
| Context-bound domain, context kind, empty-value, and exact-byte enforcement | Required-constructor and negative verification tests |
| Legacy plaintext-only coverage is not overstated | API and README documentation plus behavior tests |
| Fresh per-envelope session key | Repeated-seal randomized-output test |
| Size limits precede expensive or unsafe processing where possible | Boundary and oversized-input tests |
| Header names and values reject injection and collisions | Typed-header and faulty-adapter tests |
| Inbound cryptographic failures are opaque | Cross-category Base64, unwrap, wrong-key, padding, signature, and oversize tests |
| The pinned primitive implementation matches public standards vectors | Non-removable SM2 verification, SM3, and SM4 known-answer tests |
| Key-wrap and signature failure paths fail closed | Malformed, wrong-length, wrong-role, tamper, and wrong-key negative tests |
| Debug and errors do not echo protected values | Redaction tests using distinctive sentinels |
| Unverified plaintext is never returned | Tamper and post-decrypt failure tests |
| SDK-owned sensitive buffers are zeroizing guards | Focused implementation review and unit tests where observable |
| Cryptographic backend use matches reviewed dependency policy | Backend inventory, exact dependency pin, lockfile, feature, and unsafe-boundary checks |
| Package and export exclude prohibited material | Boundary scanner, clean-export scan, and unpacked-package scan |

If a property cannot be tested directly, the matrix identifies code-review evidence and states the limitation. It must not convert dependency behavior into an SDK guarantee.

### 7.3 Cryptographic dependency inventory

Record each dependency that implements or materially affects cryptographic behavior. For each one, capture:

- exact package and resolved version;
- enabled features and its role in signing, verification, wrapping, encryption, encoding, randomness, or zeroization;
- which SDK claims depend on it;
- known use of unsafe code or the fact that this has not been independently verified;
- public-vector and negative-test coverage exercised through the SDK;
- update and re-review policy; and
- the lockfile identity used for the RC.

The crate-level `#![forbid(unsafe_code)]` remains an own-code guarantee only. The design and release output must not extend it to dependencies. The RC check compares the resolved cryptographic dependency set and features with the inventory and fails on unexplained drift.

### 7.4 Focused adversarial tests

Preserve the existing public-standard known-answer tests and critical semantic negative tests as non-removable RC gates. Add deterministic tests only for uncovered, security-relevant boundaries found during the evidence-map review. Required categories include:

- malformed or non-canonical Base64 at length limits;
- duplicate and case-variant mapped response headers;
- oversized signatures, wrapped keys, ciphertext, and decoded plaintext;
- invalid key encodings and file-type detection;
- authentication-context kind and domain mismatches;
- malformed key-wrap values, wrong-length unwrapped keys, wrong directional roles, and wrong verification or decryption keys;
- CBC padding changes, ciphertext truncation or mutation, signature encoding mutation, and cross-category public-error equivalence;
- serialization failures before and after cryptographic verification; and
- redaction across every public error and `Debug` implementation.

Tests use neutral generated data and distinctive public test sentinels. They never add private captures, production-like identifiers, reusable private-key fixtures, or secret values to the tree.

Parser fuzzing is additive evidence. It does not replace primitive known-answer tests, cryptographic semantic negatives, or review of externally observable failure behavior and timing limitations.

### 7.5 Fuzzing

Fuzzing is focused on public or adapter-facing boundaries that accept attacker-controlled structured input. Initial targets are:

- `ResponseParts` through `HeaderProtocolAdapter::parse_response`;
- encoded `SecureEnvelope` fields through response opening with bounded test configuration; and
- typed header and request/response construction.

Fuzzing remains outside the normal library build and Cargo package. Each target documents its build command, pinned toolchain, deterministic seed corpus, pull-request smoke budget, extended scheduled budget, and triage owner. A short deterministic regression corpus runs in ordinary tests. Longer fuzz jobs run separately and retain only minimal, non-sensitive reproductions as regression tests.

A reproducible crash, panic, unbounded-allocation path, or secret-bearing diagnostic fails the applicable gate until fixed. A target or input class may be removed only by changing the documented supported-input boundary and proving that no asserted property or public API accepts it; a silent skip or release waiver is never a pass.

Fuzzing is not used as evidence that the cryptographic construction is secure. Its purpose is parser robustness, bounded failure, panic detection, and redaction preservation.

## 8. Workstream C: reproducible release engineering

### 8.1 Unified release-candidate check

Provide one documented repository-owned entry point that runs the complete public RC verification sequence:

1. confirm the intended source commit and acceptable worktree state;
2. verify that the security model, engineering evidence map, dependency inventory, API baseline, and checklist template versions are present;
3. regenerate and compare the public API snapshot;
4. compare resolved cryptographic dependencies and features with the reviewed inventory;
5. run formatting and Clippy with warnings denied;
6. run all targets, required semantic negative and known-answer tests, doctests, and strict rustdoc;
7. run the Rust 1.85 MSRV gate;
8. run dependency, license, advisory, and source policy checks;
9. build and smoke-run each required fuzz target on its pinned toolchain and budget;
10. run the boundary-scanner self-test and worktree scan;
11. create a fresh clean export from the explicit commit;
12. scan the complete export;
13. build exactly one Cargo package from that source;
14. verify the expected package file list and absence of excluded material;
15. unpack and scan the package root;
16. generate a machine-readable artifact manifest and SHA-256 checksums; and
17. report the repository-owned gates as pass or fail while marking every external gate as not evaluated in-tree.

Temporary build and export directories are created explicitly and cleaned without targeting broad or unresolved paths. The command does not use the existing working tree as the release artifact and does not infer success from a previously built package.

### 8.2 Artifact identity

The RC evidence records:

- package name and version;
- exact Git commit ID;
- source-export filename, byte length, and SHA-256 checksum;
- `.crate` filename, byte length, and SHA-256 checksum;
- `Cargo.lock` SHA-256 checksum and resolved cryptographic dependency inventory;
- toolchain, public-API, fuzz, and pinned policy-tool versions;
- security-model, engineering-evidence-map, dependency-inventory, and external-checklist template versions;
- the explicit promotion state `rc-built`; and
- the statement `external gates: not evaluated in-tree`; and
- the result of each repository-owned gate.

Generated packages and detailed external review material are not committed. The evidence format must be deterministic enough to compare two builds while allowing explicitly documented toolchain metadata to differ where byte-for-byte reproducibility is not yet guaranteed.

### 8.3 CI integration

Existing fast checks remain on pull requests. Expensive or toolchain-specific fuzzing may run on a scheduled or manually triggered job. The RC workflow reuses the same scripts as local verification so CI does not implement a separate release procedure.

No workflow receives publication credentials during this phase.

## 9. Workstream D: external readiness

### 9.1 Public checklist template

Add a neutral RC checklist template that records only:

- candidate version and commit;
- public artifact checksum and repository-owned gate status;
- whether the private denylist and fixture-fingerprint scan passed;
- whether exact-wire compatibility passed for request and response directions;
- whether rotation behavior preserved the deployed wire contract;
- independent security-review status;
- legal and open-source approval status; and
- authorized release decision.

The template contains no organization names, partner names, real field mappings, private findings, reviewer identities unless already public, ticket URLs, or private-system identifiers.

Only the blank template is committed to the public repository. A completed checklist that refers to private compatibility, policy, security, or legal evidence remains in the authorized external approval system unless a separate disclosure review approves a fully sanitized public release record.

### 9.2 External gate contract

The private release process receives the clean export and unpacked package identified by checksum. It runs:

- organization-specific denylist and fixture-fingerprint scanning;
- the exact deployed header, value-source, casing, and body-placement suite;
- opening of approved deployed-compatible responses;
- replacement-client rotation compatibility; and
- any required security and legal review procedures.

Only an authorized human or external system can mark these gates approved. The repository-owned tooling may validate the shape of a non-sensitive result but cannot create or infer approval.

### 9.3 Promotion states

The process uses distinct states:

- `candidate-source`: a named commit selected for repository checks;
- `rc-built`: repository-owned checks passed and the source export, Cargo package, manifest, and checksums were produced;
- `rc-approved`: the unchanged `rc-built` artifact received private policy, exact-wire compatibility, independent security-review, and legal/open-source approvals in authorized external systems; and
- `release-authorized`: an authorized release owner approved a separately requested publication action for the unchanged `rc-approved` artifact.

The public RC command can create only `rc-built`. It cannot infer or write `rc-approved` or `release-authorized`. Any artifact or evidence-version change returns the process to `candidate-source` and requires applicable gates to rerun.

## 10. Data and promotion flow

```text
Reviewed source commit
        |
        v
Repository-owned checks
        |
        v
Clean source export ----> complete public-boundary scan
        |
        v
Cargo package ----------> unpacked-package scan + checksum
        |
        v
Private policy scan + exact-wire compatibility
        |
        v
Independent security and legal approval
        |
        v
0.1.0 RC accepted for a separately authorized release decision
```

Promotion is monotonic: later gates may reject an artifact but may not change it. Any code, dependency, metadata, documentation, or packaging change creates a new commit and package checksum and requires the applicable gates to run again.

The required execution order is: security claims and non-claims, API review and freeze, engineering evidence and dependency review, reproducible RC construction, then external approval. A green packaging pipeline cannot compensate for an incomplete claim set, API review, or evidence map.

## 11. Error handling and reporting

- Repository-owned checks return non-zero on a failed assertion or tool error.
- A skipped check is not a pass. Platform limitations must be explicit and covered on another required platform where appropriate.
- Scanner diagnostics identify safe file locations and policy categories without printing prohibited file content.
- Cryptographic test failures use public synthetic identifiers and do not log plaintext, passwords, keys, complete envelopes, or dependency-internal errors.
- External gates have three states: pending, passed, or rejected. Missing evidence remains pending.
- A rejected or expired approval cannot be overridden by the release script.
- The RC summary distinguishes repository-owned completion from external readiness.

## 12. Milestones and acceptance criteria

### Milestone 1: API freeze candidate

- The versioned security model defines the complete claim and non-claim set used by the phase.
- The complete public surface has been reviewed.
- Every legacy or shared-role convenience has an explicit opt-in and nearby security documentation, or a documented API correction.
- Rustdoc and executable examples explain invariants and failure conditions.
- Public-enum extensibility decisions are recorded and implemented.
- All review-driven changes pass existing quality gates.
- A pinned `cargo-public-api` snapshot is captured after the surface is accepted and is reproducibly checked.

### Milestone 2: security evidence complete

- The engineering evidence map has no unclassified security-model claim and carries the non-audit disclaimer.
- Each repository-verifiable property points to a passing test or review location.
- Existing public known-answer and cryptographic semantic negative tests are mandatory RC gates.
- Identified coverage gaps have focused regression tests.
- The cryptographic dependency inventory matches the lockfile, features, and SDK use.
- Fuzz targets document their operation, build successfully, and complete a bounded smoke run without panic, unbounded allocation, or secret-bearing diagnostics.
- Remaining limitations are documented without overstating assurance.

### Milestone 3: reproducible public RC pipeline

- One documented command runs all repository-owned RC gates.
- A clean export and exactly one Cargo package are scanned successfully.
- The package contains required source, license, README, and examples and excludes prohibited fixtures and internal planning material.
- The command produces a machine-readable `rc-built` manifest, source-export checksum, package checksum, lockfile checksum, tool versions, and evidence-document versions tied to an exact commit.
- The manifest states that external gates were not evaluated in-tree.
- No publication credential or automatic publish action is present.

### Milestone 4: external handoff ready

- The neutral checklist template is complete.
- The required private compatibility and policy checks are precisely defined.
- Promotion states prevent `rc-built` from being represented as `rc-approved` or `release-authorized`.
- Public documentation states that external approvals are pending until evidence is supplied.
- The RC artifact can be handed to authorized reviewers without exposing private inputs in the public checkout.

## 13. Completion boundary

This phase is complete when Milestones 1 through 4 are satisfied for a single source commit and its identified RC package, producing the state `rc-built`. Completion means the repository side is ready and the external handoff is well-defined. It does not mean:

- the private compatibility suite has passed unless authorized evidence says so;
- an independent audit has occurred;
- production deployment is approved; or
- the crate has been published.

After external gates pass, enabling publication, tagging, pushing artifacts, or releasing to crates.io requires a separate explicit authorization and a final verification of the unchanged commit and checksum.
