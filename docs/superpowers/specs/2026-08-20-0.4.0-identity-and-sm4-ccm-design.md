# 0.4.0 Identity and SM4-CCM Envelope Design

**Status:** Approved on 2026-08-20 (owner: push `v0.3.0`, then open 0.4.0 identity-first plus one feature; feature is the reserved SM4-CCM algorithm id)

**Date:** 2026-08-20

**Target repository:** this repository (`gmcrypto-envelope-lite`)

**Target version:** 0.4.0

## 1. Purpose

Open 0.4.0 development on `main` without waiting for crates.io publication of 0.2.0 or 0.3.0, then fill the reserved AEAD algorithm identifier `0x02` with SM4-CCM as a config-pinned sibling of SM4-GCM.

This phase does not retarget `v0.2.0` or `v0.3.0`, does not `cargo publish`, and does not add a new envelope field, adapter, or cryptographic dependency.

## 2. Current baseline

Facts verified 2026-08-20 against annotated `v0.3.0` (`6363a5b601be8c95cf5b5c11e9c01c7ff180db85`), which is also `origin/main`:

- Crate version is `0.3.0`. GitHub is public. Neither 0.2.0 nor 0.3.0 is on crates.io. Publication, when it happens, is from `git checkout v0.2.0` or `git checkout v0.3.0`, never from a later `main`.
- `aead = ["gmcrypto-core/sm4-aead"]`. That core feature is atomic (`["dep:gmcrypto-simd"]`): GCM-only or CCM-only is not possible. SIMD/unsafe is already in the AEAD inventory tier.
- `AeadAlgorithm` is `#[non_exhaustive]` with one variant, `Sm4Gcm`. Frame byte `frame[1] = 0x01` is GCM. `frame[1] = 0x02` is reserved and rejected (`aead_frame_version_algorithm_and_reserved_ccm_ids_are_rejected`; fuzz seed `reserved_ccm_algorithm`).
- AEAD frame: `0x01` version ‖ algorithm ‖ 12-byte nonce ‖ ciphertext ‖ 16-byte tag. Header 14 bytes, overhead 30 bytes. AAD is the existing four-field length-prefixed transcript (`gmcrypto-envelope-lite/aead-aad/v1` ‖ frame header ‖ domain ‖ context).
- `gmcrypto-core` 1.11.0 CCM API (verified in the checksummed registry source):
  - `sm4::mode_ccm::encrypt(key: &[u8; 16], nonce: &[u8], aad: &[u8], plaintext: &[u8], tag_len: usize) -> Option<Vec<u8>>` returns `ciphertext ‖ tag`.
  - `sm4::mode_ccm::decrypt(key, nonce, aad, ciphertext_with_tag, tag_len) -> Option<Vec<u8>>`.
  - Nonce length `[7, 13]`. Tag length one of `{4,6,8,10,12,14,16}`. Canonical profile in core is 12-byte nonce, 16-byte tag.
  - A 12-byte nonce sets `q = 3`, so plaintext must be `≤ 2^24 − 1 = 16_777_215` bytes. `DEFAULT_MAX_PLAINTEXT_BYTES` is `16 * 1024 * 1024 = 16_777_216` — **one byte above that ceiling**.
  - CCM decrypts CTR plaintext before verifying CBC-MAC. On tag mismatch core `zeroize()`s the tentative buffer and returns `None`. Unlike GCM, core cannot verify-before-decrypt.
  - CCM does not call `gmcrypto-simd`; enabling it still compiles SIMD because `sm4-aead` is atomic.
- OpenSSL 3.x EVP `SM4-CCM` known-answer for the canonical profile (core `tests/sm4_ccm_kat.rs` scenario `"baseline"`, generated 2026-05-15 against OpenSSL 3.6.2): 16-byte key `0123456789ABCDEFFEDCBA9876543210`, 12-byte nonce `000102030405060708090A0B`, 16-byte AAD `FEE DFAC EDEADBEEF FEE DFAC EDEADBEEF`, 24-byte patterned plaintext, 16-byte tag. gmssl 3.1.1 does not ship `sm4 -ccm`. GB/T appendices do not cover CCM. RFC 8998 Appendix A.1 is GCM-only.
- Policy document versions are 2 (security model, API-stability, evidence, inventory, checklist). `AeadAlgorithm` is already listed as non-exhaustive, so adding `Sm4Ccm` is the documented extension path.
- Identity-train lesson from 0.3.0: bumping only `Cargo.toml` without refreshing the reviewed lock SHA **and** `fuzz/Cargo.lock` path-crate version broke CI (`--locked` fuzz tests and inventory hash). Both must move in the identity train.

## 3. Goals

- Move crate identity on `main` to 0.4.0 so `v0.3.0` and `v0.2.0` remain immutable tagged lines.
- Ship `AeadAlgorithm::Sm4Ccm` behind the existing `aead` feature, using reserved frame id `0x02`, the same 14-byte header, 12-byte nonce, 16-byte tag, and the same AAD as GCM.
- Pin the algorithm in `ClientConfig`. Never infer GCM vs CCM vs CBC from inbound bytes. A GCM client rejects CCM frames; a CCM client rejects GCM frames; both reject CBC and vice versa.
- Document CCM's decrypt-before-verify construction and its 12-byte-nonce plaintext ceiling honestly.
- Keep SM4-GCM the recommended AEAD for new integrations.

## 4. Non-goals

- Configurable CCM nonce length or tag length. This crate pins 12 and 16 so the reserved-id frame stays the 0.2.0 layout.
- A second Cargo feature (`ccm`). `sm4-aead` is atomic; a second feature would not shrink the compiled graph.
- Replay helpers, streaming / incremental CCM, server-side open-request / seal-response APIs.
- Charter §8 min-and-newest `gmcrypto-core` CI on every PR.
- Switching fuzz `transport_parts` / `typed_headers` to ContextBound schemas.
- Live `cargo publish`, retargeting `v0.2.0` or `v0.3.0`, or storing `CARGO_REGISTRY_TOKEN` in GitHub Actions.
- Changing `SecureEnvelope`, `ProtocolAdapter`, `HeaderSchema`, `KeyMaterial`, or `SecureClient` method signatures.
- New public `Error` variants.
- Replacing or weakening the mandatory SM2 signature under AEAD.
- Changing `DEFAULT_MAX_PLAINTEXT_BYTES` for CBC or GCM.

## 7. Train B — SM4-CCM

### 7.1 Wire format

Same version-1 AEAD frame as 0.2.0/0.3.0, with algorithm id `0x02`:

```
offset  size  field
0       1     frame version   = 0x01
1       1     algorithm id    = 0x02 (SM4-CCM-128, 12-byte nonce, 16-byte tag)
2       12    nonce
14      n     ciphertext      (n == plaintext length; CCM adds no padding)
14+n    16    tag
```

Constants stay `FRAME_HEADER_BYTES = 14`, `NONCE_BYTES = 12`, `TAG_BYTES = 16`, `FRAME_OVERHEAD_BYTES = 30`. The minimum valid frame is still 30 bytes (empty plaintext).

`wrapped_session_key` and `signature` are unchanged.

AAD is unchanged: `AuthenticationMode::aead_aad` already binds the 14-byte header, so the algorithm id is in the tag.

### 7.2 Primitive mapping

Seal:

1. Draw a fresh 16-byte session key and a fresh 12-byte nonce (same as GCM).
2. Build AAD from the assembled 14-byte header.
3. `mode_ccm::encrypt(&session_key, &nonce, &aad, plaintext, 16)`. `None` is `Error::Encryption`.
4. Emit `cipher = Base64(header ‖ ciphertext ‖ tag)` where the core buffer is already `ciphertext ‖ tag`.

Open (after the existing encoded-size, Base64, floor, version, algorithm-pin, and ciphertext-length checks):

1. Reconstruct AAD; mode/context mismatch maps to `InvalidEnvelope` (same as GCM).
2. Pass `ciphertext ‖ tag` to `mode_ccm::decrypt(..., 16)`. `None` is `InvalidEnvelope`.
3. Wrap successful plaintext in `Zeroizing` before signature verification, matching GCM.

Do not split CCM into a separate payload module. Dispatch inside `src/envelope_crypto/aead.rs` on `AeadAlgorithm`.

### 7.3 Algorithm pinning

`fn algorithm_byte` maps `Sm4Gcm → 0x01`, `Sm4Ccm → 0x02`. Open requires `frame[1] == algorithm_byte(configured)`. Unknown ids remain rejected.

Rename the GCM negative that currently says “reserved CCM”: a GCM client still rejects `0x02` and `0x7f`; those ids are no longer globally reserved, they are **not this client's algorithm**. Keep the fuzz corpus filename `reserved_ccm_algorithm` (renaming tracked corpus files loses history); comment that it is a GCM-client rejection of id `0x02`.

### 7.4 Plaintext ceiling

```rust
#[cfg(feature = "aead")]
pub const SM4_CCM_MAX_PLAINTEXT_BYTES: usize = (1 << 24) - 1; // 16_777_215
```

Export from the crate root under `feature = "aead"`.

`ClientConfig::build`:

- CBC and GCM: omitted `max_plaintext_bytes` still defaults to `DEFAULT_MAX_PLAINTEXT_BYTES` (16 MiB).
- CCM: omitted `max_plaintext_bytes` defaults to `SM4_CCM_MAX_PLAINTEXT_BYTES`.
- CCM: an explicit value `> SM4_CCM_MAX_PLAINTEXT_BYTES` is `Error::Configuration { field: "max_plaintext_bytes" }`.
- CCM: `0` remains `Configuration { field: "max_plaintext_bytes" }` (existing rule).
- GCM/CBC: an explicit 16 MiB remains valid.

Do not silently clamp. Do not change the CBC/GCM default. A caller who copies a GCM builder and only switches the algorithm, while also setting `.max_plaintext_bytes(DEFAULT_MAX_PLAINTEXT_BYTES)`, gets a configuration error rather than a seal-time `Encryption`.

Seal of exactly `SM4_CCM_MAX_PLAINTEXT_BYTES` must succeed. The encoded Base64 bound for CCM open uses `max_plaintext_bytes + 30` with the client's configured (and therefore already CCM-legal) limit.

### 7.5 Public API

```rust
#[cfg(feature = "aead")]
#[non_exhaustive]
pub enum AeadAlgorithm {
    Sm4Gcm,
    Sm4Ccm,
}
```

`Sm4Ccm` rustdoc: 12-byte random nonce, full 16-byte tag, frame id `0x02`; not a negotiation field; CCM decrypts before verifying (core wipes on tag failure); plaintext ceiling `SM4_CCM_MAX_PLAINTEXT_BYTES`; new integrations should prefer `Sm4Gcm`.

`EnvelopeMode::Aead(_)` already rejects a configured IV for any algorithm; no new IV rule.

No new `Error` variants. Inbound CCM failures stay `InvalidEnvelope`. Outbound primitive `None` stays `Encryption`. Oversize plaintext stays `MessageTooLarge`. Builder misuse stays `Configuration`.

### 7.6 Security-model claims (Train B)

Bump **Model version** 2 → 3 and **Evidence version** 2 → 3. Inventory version stays 2 (no new packages); update the AEAD-tier `gmcrypto-core` row from “Adds SM4-GCM sealing…” to “Adds SM4-GCM and SM4-CCM sealing…”.

Inbound AEAD paragraph must distinguish:

- GCM: tag verification precedes plaintext materialization (core).
- CCM: CTR decryption precedes CBC-MAC verification (mode construction). Unverified plaintext is not returned; core wipes the tentative buffer on tag failure; this crate still never yields plaintext on `None`.

Non-claims: CCM does not add replay protection; it does not make the SM2 signature optional; it does not avoid compiling `gmcrypto-simd`.

## 8. Testing strategy

TDD. GCM tests stay; they must keep passing unmodified except the reserved-id test rename/comment and helpers that grow an algorithm parameter.

### 8.1 Known-answer

Add `sm4_ccm_matches_openssl_sm4_ccm_baseline` in `tests/standard_vectors.rs` under `feature = "aead"`, pinning core `mode_ccm` against the OpenSSL baseline vector in §2 (name the source in the test, same convention as the RFC 8998 GCM KAT). Assert encrypt matches `ct ‖ tag`, decrypt recovers plaintext, and a flipped tag returns `None`. Do not invent vectors. Do not pin 7-byte nonce or short-tag profiles; this crate does not ship them.

### 8.2 Round-trip and composition (CCM)

Mirror GCM coverage with CCM-configured peers (`test_support::ccm_peers` / `aead_config` parameterized by algorithm):

- Both directions, distinct roles; frame `[0] == 0x01`, `[1] == 0x02`; frame length `plaintext.len() + 30`.
- `LegacyPlaintext` and `ContextBound`.
- Empty, max-configured, and UTF-8 plaintext.
- Length sweep at the same LENGTHS as GCM (frame overhead is identical).
- Fresh session key and nonce per seal.
- Context kind mismatch: outbound `AuthenticationContext`, inbound `InvalidEnvelope`.
- AAD mismatch (wrong domain) is `InvalidEnvelope`.

### 8.3 Negatives (CCM)

Each `InvalidEnvelope`, indistinguishable:

- Version tamper; algorithm `0x01` (GCM) and `0x7f`; frames of 29 bytes and truncated tag.
- Nonce, first/middle/last ciphertext byte, last tag byte, all-zero tag.
- Non-canonical / invalid Base64; malformed and wrong-length wrapped keys; tampered signature; wrong decryption/verification keys.
- Encoded vs decoded over-bound split (`MessageTooLarge` vs `InvalidEnvelope`), using a CCM max small enough that the 30-byte overhead still produces the same public Base64 arithmetic as the GCM test (limit 17 / 18).

### 8.4 Discriminating AAD test (CCM)

Mirror `aead_seal_gcm_tag_binds_literal_label_header_domain_and_context`: unwrap the session key, rebuild the four-field AAD, and assert `mode_ccm::decrypt(..., 16)` succeeds for the literal AAD and fails when any of label, header, domain, or context is changed. Must not mutate the sealed envelope.

### 8.5 Downgrade / cross-algorithm

- GCM client rejects CCM envelope; CCM client rejects GCM envelope.
- CCM client rejects CBC envelope; CBC client rejects CCM envelope.
- Existing GCM↔CBC test remains.
- No API path selects the algorithm from envelope bytes.

### 8.6 Configuration

- CCM builds without IV; IV + CCM is `Configuration { field: "iv" }`.
- Omitted max on CCM equals `SM4_CCM_MAX_PLAINTEXT_BYTES`.
- Explicit `DEFAULT_MAX_PLAINTEXT_BYTES` on CCM is `Configuration { field: "max_plaintext_bytes" }`.
- Explicit `SM4_CCM_MAX_PLAINTEXT_BYTES` on CCM builds; seal of that many bytes succeeds.
- GCM omitted max remains `DEFAULT_MAX_PLAINTEXT_BYTES`.

### 8.7 Integration

`tests/aead_envelope.rs`: CCM `SecureClient` round-trip through `HeaderProtocolAdapter`; CCM↔GCM and CCM↔CBC mutual rejection.

### 8.8 Fuzz

New target `aead_ccm_envelope`, cloned from `aead_envelope` with a CCM-configured client (`support::ccm_client` / `ccm_valid_envelope` / `ccm_encoded_values`). Keep `aead_envelope` GCM-only, including seed `reserved_ccm_algorithm`.

CCM corpus: `full_valid_open` plus the same structural/mutation categories as GCM (frame floor ±0/−1, nonce/cipher/tag mutations, encoded bounds, `wrong_gcm_algorithm` with `frame[1] = 0x01`). Each seed declares an explicit open outcome in `fuzz/tests/scenarios.rs`.

## 11. Risks and accepted trade-offs

- **CCM decrypt-before-verify.** Inherent to CBC-MAC-then-CTR. Mitigated by core's wipe on `None` and by never returning plaintext on failure. Documented in the security model so GCM's verify-before-decrypt sentence is not read as covering CCM.
- **12-byte nonce ceiling is one byte below the crate default max.** Explicit configuration error rather than a surprising seal-time `Encryption`. CCM's omitted-max default is the ceiling, not 16 MiB.
- **Compiled AEAD graph still contains SIMD unsafe.** Unavoidable; already inventoried. CCM itself is software SM4.
- **Two AEAD algorithms double part of the test matrix.** Accepted: GCM stays fully tested; CCM is not “GCM with a different byte”.
- **Fuzz seed name `reserved_ccm_algorithm` becomes historically named.** Accepted; corpus bytes stay.
